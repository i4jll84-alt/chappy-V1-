# 第1段階の設計

対象は単一銘柄・明示期間の日次株価取得。注文・学習・バックテストは含まない。
ユーザーの本仕様は [development-instructions.md](development-instructions.md)。

## データの流れ

1. Pydanticで設定を検査する。Stage=1、実取引=falseのみ許可。
2. 固定した公式HTTPS URLにAPIキー認証で要求。タイムアウト30秒、最大4試行。
3. 成功応答のJSON本文bytesをRawへ保存する。認証ヘッダーは保存しない。
4. 品質検査、版管理、ページ履歴、次ページ情報を同一DuckDBトランザクションで確定。
5. DuckDBからParquetの新しい世代を作成して読み戻す。全ファイル成功後だけlatest.jsonを置換。
6. 非空・品質エラーなし・Parquet検証成功時に取得ジョブをcompleteと記録。

RawとParquetは `data/jquants/` の下に置く。取得データ、ログ、DBをGitへ入れない。
rawファイル名は毎回異なり、訂正や異常データでも上書きしない。クラッシュでDBに登録されない
Rawが残る場合は孤立ファイルとして保持する。自動削除はしない。
単一PC・単一writerを前提とする。別プロセスの書込みはDuckDBロックで拒否される。
同じアカウントを使う別アプリのAPI呼出しはレート制御の対象外なので、併用時は429待機が生じ得る。

## 保存するテーブル

| テーブル | 役割 |
|---|---|
| jobs | 固定検索条件、プラン申告、開始/更新日時、checkpoint、完了/空/品質異常/失敗 |
| attempts | HTTP試行時刻、ステータス、分類。認証情報・応答エラー本文を保存しない |
| pages | Rawパス、SHA-256、取得日時、取得件数、要求/次のページ情報 |
| observations | 全取得行と版IDの対応。正規化不能な行もRaw位置を残す |
| price_versions | 日付・コード・未調整/調整済価格・PIT時刻・訂正前版への参照 |
| quality_issues | 対象行、検査名、重大度。値の自動補完/削除をしない |
| prices_current (view) | 銘柄・日付ごとの最新取得版。履歴は残す |

同一内容の再取得は新しいprice_versionsを作らずobservationsだけ増える。
内容A→B→Aという訂正は3版として残す。財務など別データのスキーマは未実装。

## Point-in-Time

公表日時published_at、提供元更新日時source_updated_atは不明のためnull。
observed_atは応答受信完了、ingested_atはDB登録処理時刻として別々に保存する。
初期available_atはobserved_atの1秒後とし、ルール名とobserved_onlyの信頼区分を保持する。
これは市場への公表時刻を推定した値ではなく、ローカルで確認した後にのみ使用する保守的制約。
取得前の過去時点に遡るバックテストにはそのまま使えない。初回取得前の訂正履歴も復元できない。
as_ofは利用可能時刻で絞って最新の版を選び、品質エラーの版を除外する。
調整済み株価は後日の分割等で変化し得るため、過去の当時値とは扱わない。

## 再実行・再開

同じ検索条件の取得が失敗したら、同じコマンドを実行すると最後の確定ページから再開する。
すでにcomplete/empty/quality_failedの取得を再要求するには `--refresh` を指定する。
期限切れページ情報やページング中のデータ更新を疑う場合も `--refresh` で先頭から再取得する。
ページング途中の提供元更新による完全なスナップショット整合性は保証されない。
Parquet出力が失敗してもDBは保持し、再実行時はHTTPを呼ばず出力をやり直す。
latest.jsonを参照せず世代フォルダーをglobで一括読込みすると重複するので禁止する。
完了状態の更新はParquet出力を含むDBトランザクションで確定し、jobs.parquetとDBを一致させる。
ファイルとDBを跨ぐ原子的コミットはないため、強制終了で未確定世代が残り得る。
再開判定はDuckDBを正とし、同じコマンドで再出力する。

差分取得は明示した下限から連続して完了した取得区間だけを進め、末尾7暦日を重ねる。
下限より後に部分取得した区間があっても、未取得区間を飛ばさない。
この重複期間外の訂正は自動検出できないため、必要な全期間を定期的にrefreshする。
市場カレンダーとの照合、上場期間判定、欠落営業日検出は未実装。取得ジョブcompleteは
API応答の保存成功を意味し、対象期間の全営業日の網羅性を保証しない。

## 品質と制約

不正日付、英数字コード、必須キー欠落、部分null、有限正数、OHLC矛盾、調整値のnull対応、
重複、検索条件外の日付/銘柄を検査。全OHLC・出来高・売買代金nullは無約定の正常区分。
品質エラー行はRawに保持し、正規化できる値もエラーフラグ付きで保存する。
内容が同じでも品質判定が変われば検証版を追加し、過去の判定は改変しない。
非有限数値は正規化数値列をnull、payload_jsonを明示的な$invalid_numberタグとして記録する。
Rawには受信した本文をそのまま残し、このタグ付けを元データの修正とは扱わない。
無約定の理由（売買停止等）は判別しない。上場マスター照合と分割倍率の時系列監査は未実装。
価格が大きく動いたことだけを理由とする削除や補正はしない。

## テスト方針

HTTPの模擬応答で401/403/429/5xx/timeout/ページングを検証し、
実DBと実Parquetを使う結合テストで訂正・冪等性・復旧・PIT境界を確認する。
実APIテストは明示的に有効にした場合のみ実行し、未実施はskipとして報告する。
