# 複数データソース・カバレッジ監査 作業報告

## 工程完了報告

**1. 工程名**

第1段階の保存済み株価・TOPIX・取引カレンダーを横断する、読み取り専用カバレッジ監査の設計・実装。

**3. 実装した機能**

CLI `audit-coverage --code --from --to [--decision-at]` を追加。指定条件に完全一致する取得ジョブを
データセットごとに選び、判断時点の状態、完了時刻+1秒と各行の `available_at`、保存済み品質結果、
価格/TOPIXと東証営業日のカバレッジを検査する。状態は取得失敗・未完了・品質異常・判断時点での
判定不能・日別カバレッジ不足を区別する。全nullの価格行は無約定として存在扱いとする。

元catalogは読み取り専用で開き、API要求、マイグレーション、値の削除・補完・修正を行わない。
監査ごとのUUID付きreceiptを `data/jquants/audits/coverage/` に追加保存する。異なるcatalog間で
単一の原子的スナップショットは保証されず、DBに保存済みのハッシュはRawファイルを再読込して
改ざん検知するものではない。Parquetファイルの整合性検査も行わない。監査仕様と制限は
[設計文書](coverage-audit.md)を参照。

**5. 実行したテスト**

統括担当が既存データに対してCLIを2回実行し、両方のJSON出力と保存receiptを比較した。新規API要求は
行っていない。実装担当がfocused pytestを実行し、統括担当が指定basetempで全体pytest、全体Ruff checkと
format checkを実行した。5件のskipは実API opt-inテストであり、今回の読み取り専用監査では追加のAPI要求が
不要なためである。

**7. 発見した問題**

独立したGPT-6 Astra / Highレビューでは、修正後の確認範囲に未解決の重要な問題はなかった。
レビューで見つかった孤立版参照の問題は修正し、回帰ケースを追加した。監査仕様として、判断時点の過去ジョブ状態を
履歴から確定できない場合は判定不能とし、後日更新された状態へ切り替えない。営業日に株価行がない場合も欠落原因は確定せず、売買停止・
上場状態・提供元の未収録などの区別はできない。

**8. 未確認事項**

実データでの確認は銘柄86970、2026-10-01〜2026-10-22の保存済み価格・TOPIX・カレンダーに限る。
他銘柄・他期間・欠落日・全null無約定行・quality_failed・blocked状態の実データケースは今回の監査実行では
確認していない。pytestの5 skippedは別の実API opt-inテストであり、今回の監査では追加ネットワーク取得を
行っていない。

**9. 既知のリスク**

今回の監査は各DuckDBを個別に読むため、データセットを跨ぐ同一時点の原子的整合性はない。receiptは選択した
ジョブ・版・記録済みハッシュを結び付けるが、Rawファイルの現物ハッシュ再計算、Parquet整合性検査、
全アーカイブの改ざん検知を行わない。初回取得以前の提供元訂正・状態遷移、未取得期間の過去状態は
復元できない。監査は全市場・全期間の網羅性を保証しない。

運用上の残るカバレッジをレビューする。第1段階完了条件の確認前に第2段階へ進まない。
