# 楽天RSS読取の部分失敗と再試行（2026年11月19日）

研究用Excelの読取を修正した。取得元・銘柄・戦略の売買条件・記録済みの判定時刻は変えていない。

## 調査結果

11月19日の読取4,104回のうち、成功3,949回、全体失敗155回。失敗の内訳はCOM呼出拒否145回、Excel未登録2回、対象ブック待ち7回、Readyが偽の1回。155回すべての後に成功記録がある。ただし、後続の成功は失敗時点のデータの復元を意味しない。

COM呼出拒否のHRESULTは0x80010001。[Microsoftの定義](https://learn.microsoft.com/en-us/windows/win32/com/com-error-codes-3)は呼出先による拒否であり、Excel内部の再計算・編集・ダイアログなど、どの状態が直接の契機だったかは保存原本では確定できない。08:15～08:30のApplicationイベント1000/1002にもExcelの異常終了記録はなかった。

全体失敗のうち109回はReadyの取得段階、12回は指数の取得段階。29回は先行する別段階でも再試行枠を消費していた。旧実装は1回のスナップショットの全プロパティで再試行2回を共有し、200+400ミリ秒で打ち切っていた。また、最後に読む補助指数の例外で、それまでに検査済みの株価・分足まで破棄していた。

9360の13:30判定で必要な13:25～13:29の分足は、正規化DBだけでなく読取原本にも存在しなかった。気配の最終約定・累積出来高と公式日足の照合では、約定が増えず分足が返らなかった状況と整合する。保存側の削除・切捨ての証拠はない。将来の約定、日足、別銘柄から足を補完せず、元の判定不能を保持した。

詳細な時刻・価格・出来高・原本照合はローカルの data/offline-verification/rakuten-20261119-read-fix/ に保存。データとログはGitに含めない。

## 修正内容

- COMの一時エラーだけを、プロパティごとに200、400、600ミリ秒（以後600）で再試行する。スナップショット全体の追加待機時間は合計1,800ミリ秒まで。以前より最大1,200ミリ秒増える。COM呼出自体の所要時間を含む上限ではなく、読取プロセスの45秒タイムアウトは維持する。
- 永続的なエラー・null・不正な行列・銘柄や数式の不一致は従来どおり検出する。各再試行の段階、プロパティ、HRESULTに加え、待機時間・その呼出内の回数を原本に残す。
- 指数読取だけの失敗では、検査済みの株価・分足を保存し、指数は欠測にして index_issue を残す。指数の欠測を全体成功で隠さず、状態表示にも「指数の読取は自動再試行中」を出す。復旧後は表示を解除する。
- 全体成功件数は株価スナップショットの保存成功を表す。指数の部分失敗は index_issue を別途集計する必要がある。旧記録の155回を新方式で成功に書き換えたり、将来の失敗減少数を予測値として扱ったりしない。

## 検証と制約

Windows PowerShellで実際の製品関数を読み込み、COM例外を出すテストオブジェクトで再試行・打切り・非一時エラー・指数の各読取段階の失敗を再現した。取得済み株価と分足の保持、指数の数式・行列検査、原本保存、指数復旧時の状態解除を確認した。実際のExcelに対する稼働中の障害再現ではない。

関連47件、全体1,682件と8 subtestsが合格し、5件はスキップ。全体試験は302.16秒。既存A0-5のNumPy timedelta非推奨警告が5件残る。Ruff check合格、書式検査344ファイル合格。全体静的検査で検出した既存のimport区切りも空行1行のみ修正した。原本DBと既存の固定条件再生・再実行の計11ファイルは、修正前の検証記録および診断前後でSHA-256が一致した。

この修正による営業中の読取失敗率・分足遅延の改善幅は未検証。次の実取得で全体失敗・再試行復旧・指数部分失敗・取得遅延を分けて評価する。Excelの起動・対象ブックの読込自体を省略したり、欠測を埋めたりする修正ではない。
