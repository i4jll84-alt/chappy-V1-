# 寄り前の日付待機と取得の開始

変更日: 2026-10-28。作業場所はローカルの個別株自動売買ツールV1。

## 原因と改善

10月28日07:39と07:49の開始前検査では、Excelのセルは読めたものの、
日付が前日だったため3件とも`current_date_not_today`になった。
旧スクリプトはその時点で終了し、その後に日付が更新されても自動で再確認しなかった。
当日の常時取得開始は10:05:19 JST。日付が切り替わった正確な時刻は記録されていない。
利用者が開始操作をしても待機を継続できなかった、起動処理側の不足を修正した。
取得していない時間帯を復元・補完したり、取得済みと扱ったりはしない。

## 新しい開始手順

1. 従来どおり本人がMarketSpeed IIへログインし、Excelを「接続中・発注不可」にする。
2. 「RSS接続確認して開始」を開き、確認項目をチェックして開始する。
3. 取得Pythonプロセスが排他ロックを確保し、残存Rawの復旧後に3件を検査する。
4. 過去の日付以外に異常がなければ、`waiting_for_current_date`として待機する。
   各検査の終了後30秒待って、再び3件を検査する。Excel読取時間が加わるため、厳密な30秒周期ではない。
5. 3件すべてが当日の日付で既存の品質検査を通ると、自動で通常取得へ進む。

確認画面を閉じ直して再操作する必要はない。待機中もPCとアプリは稼働させておく。
待機プロセスも二重起動を防止する。OSへの常駐登録や翌朝の自動起動は追加していない。
未来の日付、読取失敗、価格・時刻・式・対象銘柄の異常などは待機の許可対象に含めず、
記録を保存・照合してエラー終了する。エラーを直してから利用者が改めて開始する。

## データと停止の扱い

- 元の`validate_read`や仮想台帳の鮮度検査は変更していない。
  前日以前の値は`attention_required`、`current_date_not_today`のまま保存する。
- 休日を推測して「正しい前営業日」と認定するものではない。過去の日付は待機条件だけに使う。
- 検査データは通常取得と同じ`data/rss-continuous/runs`、Raw、DBに保持する。
  待機中は30検査ごと、開始判定時と終了時にもParquetを書き出す。
- 検査データは正常な当日の値も含めて仮想台帳では観測専用として処理し、仮想約定を発生させない。
  通常取得への移行後に既存のペーパー処理を使う。実発注・訂正・取消は引き続き禁止。
- `samples`には開始検査の読取試行も含む。`startup_samples`と`startup_attempts`で内訳を区別する。
  `cycles_completed`は通常取得のサイクル数で、待機検査の回数を含まない。
- 赤い停止ボタンとCtrl+Cで待機を中止できる。元の起動日の16時期限を保持し、
  16時到達や翌日へのスリープ復帰でも新しい読取を始めず、保存・照合して終了する。
- 16時以降の起動や`--recover-only`では開始検査を行わず、オフライン後処理だけを実行する。
- 当日という検査結果を、RSS接続状態・厳密な提供元更新日時・市場約定の保証にはしない。
  `freshness_verified=false`や不明な提供元日時の扱いは維持する。

直接CLIを使う場合は`--wait-for-current-date`を指定する。通常のショートカットはこの指定を追加済み。
既存コードの呼出しや検証用の直接起動は、指定しない限り従来の動作を維持する。
