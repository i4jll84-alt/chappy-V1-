# モック注文管理の初期設計

第9章の入口として、実発注しないローカルモックで注文状態と障害回復を検証する。
実際の楽天証券RSS、Excel、証券口座、通信APIへ接続する処理は含めない。
モックの成功を証券会社への接続成功や実運用可能の証拠にしない。
初期範囲は、明示した一つのモック取引セッション内の固定価格・制度・費用・口座である。
複数日にまたがる費用や市場変動は、前工程の時系列シミュレーターと別の検証対象となる。

## 保存と送信

注文の意図と識別子を送信より前に永続保存する。同じ識別子・同じ内容の再要求で
新しい注文を増やさず、同じ識別子で内容を変えた要求は拒否する。
送信の応答を受け取れなくても、未受付と判断して再送しない。
相手側の状態を照合してからローカル状態を更新する。

状態の更新と監査履歴は一つのDBトランザクションで確定する。
プロセス再起動でも送信中・結果不明・取消中の状態を消さない。
注文ログとモック相手側の記録を残し、障害を起こした後から経緯を確認できるようにする。
再起動で口座を初期残高へ戻さず、照合した約定から更新した残高を復元する。

注文側と相手側のDBを同じトランザクションで確定できるとは扱わない。
送信前後の不確実な区間を保存し、照合で解消する。相手側に見つからないという応答だけで
自動再送しない。再起動時に設定の内容が変わった場合も、既存状態を新しい設定で読み替えない。

## 配分結果との接続

`execution.adapter.intents_from_plan`は、前工程の完了した合成配分結果について
ハッシュと元入力からの再計算結果を確認し、受入候補の数量だけを渡す。
モックで使う指値価格と有効期限は別途明示する。受入候補以外の価格指定や欠落は拒否する。
注文IDは配分結果のハッシュ・銘柄・売買区分から作り、同じ候補に対する価格や期限の変更で
別注文IDを発行しない。同じIDで異なる内容が来た場合は注文管理側が拒否する。

ハッシュは認可や本人確認の証明ではない。複数戦略の統合候補は注文上のラベルを
`portfolio`とし、元の数量帰属は保存した配分結果のハッシュを通じて参照する。
この接続で送信を行うことはなく、その後もモックの余力・数量・期限などの検査が必要となる。

## 約定と取消

取消要求は取消確定と区別する。取消と約定が競合した場合にも、確定した約定を消さない。
部分約定を累積数量と約定識別子で照合し、同じ情報を再び受けても二重に計上しない。
注文数量を超える約定や、識別できない注文・建玉差異は正常として取り込まない。

## 安全性の境界

新規注文の数量・金額・余力・保有上限、空売り可否、日次損失、緊急停止を
明示したモック条件で検査する。未知の状態では新規注文を止める。
新規送信前には、ローカルの残高だけでなくモック側の口座と注文一覧も照合する。
未反映の約定や未知の注文があれば照合・停止解除が済むまで新規送信しない。
これは固定モック内の事前観測であり、実証券会社を含む分散トランザクションの保証ではない。
保有や未約定の拘束を、単なる通信失敗や取消要求だけで解放しない。
緊急停止だけを理由に保有を減らす売却・返済を禁止しない。ただし現在の現金余力の
下限を保守的に適用するため、既に資金・担保が不足した口座では決済も拒否する場合がある。
この初期実装は強制決済や資金不足からの清算を解く機能ではない。
実証券会社の注文識別・照合・取消仕様を推定して実装することはしない。

この工程はローカル障害試験であり、実株価のペーパートレードとは異なる。
連続した市場価格更新、貸株費用の日次計上、企業行動、実口座の鮮度確認、
ExcelやRSSのOS上の異常停止はこのモックで検証したことにはならない。
実資金注文は引き続き別途の明示承認が必要。
