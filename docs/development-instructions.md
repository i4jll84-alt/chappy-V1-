# 第1章　開発目的と基本原則

## 1.1 開発目的

日本の個別株を対象に、短期・スイング・中期の複数戦略を統合した自動売買システムを新規構築する。

株価、出来高、財務、信用需給、機関投資家の公開情報、市場環境などを分析し、売買候補の選定、ポートフォリオ管理、バックテスト、将来的な楽天証券への自動発注までを実現する。

各分析機能には、その目的に適した統計モデル、機械学習モデル、ルールベースを個別に採用する。

開発にはCodexを使用し、作業の重要度に応じてGPT-6 Astra、GPT-6.1 Sol、GPT-6 Lunaを使い分ける。

## 1.2 最重要原則

以下をすべての工程で遵守する。

1. 正確なデータを使用する。
2. 未来情報の混入を防止する。
3. チェリーピッキングを禁止する。
4. 過剰最適化を抑制する。
5. バックテストの再現性を確保する。
6. 実際の取引コストを考慮する。
7. AIの予測と確認済み事実を区別する。
8. 誤発注や過大損失を防止する。
9. 複雑なモデルより、検証で有効性を確認できたモデルを優先する。
10. 実運用前に十分な検証と模擬運用を行う。

最優先事項は、見かけ上の高収益ではなく、検証の信頼性と実運用の安全性である。

# 第2章　システム基本仕様

## 2.1 対象市場

- 東京証券取引所上場の個別株
- プライム・スタンダード・グロース市場
- 過去の上場廃止銘柄も、データが利用可能な範囲で検証対象とする
- ETF・REIT・投資信託は初期対象外
- 整理銘柄・監理銘柄などは別途リスク判定を行う

対象銘柄を現在の上場企業だけに限定して、過去のバックテストを実施してはならない。

## 2.2 売買取引区分

### 初期実装対象

| 取引 | 対応 |
|---|---|
| 現物買い | 対応 |
| 現物売り | 対応 |
| 信用新規売り | 対応 |
| 信用返済買い | 対応 |

### 将来の拡張候補

| 取引 | 対応 |
|---|---|
| 信用新規買い | 将来検討 |
| 信用返済売り | 将来検討 |

信用買いについては、現物買いとの資金効率、買方金利、レバレッジ、最大ドローダウン、追証リスクを比較したうえで採用を判断する。

第1〜第3段階では信用買いを実装する必要はない。

ただし、将来の追加が大規模なシステム改修にならないよう、取引区分・建玉管理・資金管理を拡張可能な構造にする。

## 2.3 保有期間

複合型を採用する。

| 戦略 | 初期検証範囲 |
|---|---|
| 短期 | 1〜5営業日 |
| スイング | 6〜20営業日 |
| 中期 | 21〜60営業日 |

それぞれ独立した売買戦略として構築し、単独成績と複合運用成績を比較する。

保有期間は固定の最適値ではなく、検証対象の範囲とする。

## 2.4 利用サービス

- J-Quants API V2
- 楽天証券
- マーケットスピード II RSS
- 必要に応じてTDnet
- 必要に応じてEDINET
- 必要に応じて日本証券金融等の信用関連情報

追加するデータソースについては、取得方法・利用規約・過去データの範囲を確認する。

# 第5章　第1段階：データ基盤構築

## 5.1 開発目標

J-Quants APIから日本株データを取得し、品質を確認したうえでDuckDBとParquetに保存する。

この段階では実際の証券注文を行わない。

また、株価予測AIの学習も実施しない。

## 5.2 使用技術

- Python
- J-Quants公式Pythonクライアント、または公式仕様に準拠したHTTPクライアント
- pandas
- NumPy
- DuckDB
- PyArrow
- Pydantic
- pytest
- Ruff
- Git

原則としてAIによるデータ自動補完や異常値削除を行わない。

## 5.3 J-Quants API接続

以下を実装する。

1. V2 APIへの接続
2. APIキー認証
3. 契約プランと取得可能データの確認
4. タイムアウト処理
5. レート制限への対応
6. ページネーション処理
7. 再試行
8. 差分更新
9. 中断後の再開
10. API取得ログ

APIキーは環境変数で管理する。

認証情報をGit・ログ・画面に表示しない。

## 5.4 取得するデータ

### 優先度A

- 銘柄マスター
- 日次株価四本値
- 出来高
- 売買代金
- 株式分割・併合関連情報
- 財務・決算情報
- TOPIX
- 取引日カレンダー

### 優先度B

- 信用取引残高
- 空売り残高報告
- 投資部門別売買状況
- 業種・市場区分

### 優先度C

- 大量保有報告書
- 大株主情報
- その他の有効なデータ

各データの取得可否、収録期間、更新頻度、提供プラン、時点情報の有無を確認する。

存在しないエンドポイントを推測して実装しない。

利用できないデータは欠損・未契約・未提供を区別して記録する。

## 5.5 データベース設計

保存先はDuckDBとParquetを基本とする。

保存するデータを次の3層に分離する。

### Raw

APIから取得した元データ。

### Normalized

型・日時・銘柄コードなどを正規化したデータ。

### Processed

分析用に加工したデータ。

元データと加工データの対応関係を追跡できるようにする。

## 5.6 Point-in-Time管理

必須項目：

- 対象日
- 情報公表日時
- データ取得日時
- 売買判断への利用可能日時
- データ更新日時
- データ提供元
- 訂正履歴
- 日時情報の信頼区分

公表日時が不明な場合は、推測値を確定情報として保存しない。

利用可能日時が正確に再現できない場合は、保守的な遅延ルールを設ける。

## 5.7 データ品質管理

以下を検査する。

- 欠損
- 重複
- 異常な価格
- 不正な日付
- 株価・出来高の矛盾
- 銘柄コード不一致
- 株式分割処理の不整合
- 財務データの日時矛盾
- 更新漏れ
- 取得失敗

異常値を検出しても、原則として自動削除しない。

## 5.8 第1段階の完了条件

以下を満たした場合のみ完了とする。

1. J-Quants APIとの接続が成功している。
2. 株価データを正常に取得できる。
3. Parquetに保存できる。
4. DuckDBから読み出せる。
5. 重複・欠損・異常値を検査できる。
6. データ取得履歴を保存できる。
7. 再実行しても重複が発生しない。
8. 自動テストが正常に終了する。
9. 未確認事項と制限事項を文書化している。

実際のAPI接続ができない場合、モックテストが成功したことだけで工程完了としない。

# 第6章　第2段階：バックテスト基盤

## 6.1 開発目標

短期・スイング・中期戦略を、公平かつ再現可能な条件で検証できるシステムを構築する。

推奨開発モデル：GPT-6 Astra / High

## 6.2 使用候補

- Backtrader
- VectorBT
- pandas
- NumPy
- SciPy
- statsmodels
- DuckDB

ライブラリは実際の要件適合性を確認して選定する。

## 6.3 必須機能

- 現物買い・売り
- 信用新規売り・返済買い
- 保有期間管理
- ポジション管理
- 売買手数料
- スリッページ
- 貸株料
- 逆日歩
- 配当・権利処理
- 株式分割・併合
- 売買単位・呼値
- ストップ高・ストップ安
- 流動性制約
- 信用売り規制
- 約定不能時の処理

楽天証券における過去の信用売り在庫や規制履歴が不足している場合、その制約を明示する。

- 約定できない価格で売買すること
- 不利な年度を除外すること
- テスト期間に合わせてパラメータを変更すること

## 6.5 評価項目

- 累積リターン
- 年率リターン
- TOPIX超過リターン
- シャープレシオ
- 最大ドローダウン
- プロフィットファクター
- 勝率
- 平均利益・平均損失
- 売買回数
- 平均保有期間
- 年度別成績
- 買い・信用売り別成績
- 取引コスト
- リスク調整後成績

資金配分方法、現金比率、リバランス頻度を明示する。

## 6.6 検証手法

- 時系列分割
- ウォークフォワード検証
- アウトオブサンプル検証
- 必要に応じたパージ・エンバーゴ
- 最終未使用期間での一度限りの評価
- 過去の市場急変期を含むストレステスト

探索したパラメータやモデルの履歴をすべて保存する。

## 6.7 第2段階の完了条件

単純な基準戦略について、同じ入力から同じバックテスト結果を再現できること。

注文・約定・損益計算・取引コストの自動テストに合格すること。

未来情報混入についての監査が実施されていること。

# 第7章　第3段階：AI分析・予測モデル

## 7.1 開発目標

短期・スイング・中期に適した予測モデルを構築し、基準戦略と比較する。

モデルは必要に応じて個別採用する。

## 7.2 分析別モデル候補

| 分析機能 | 第一候補 | 比較候補 |
|---|---|---|
| 短期予測 | LightGBM | XGBoost・ロジスティック回帰 |
| スイング予測 | LightGBM | CatBoost・XGBoost |
| 中期予測 | CatBoost | LightGBM・Elastic Net |
| 財務・決算分析 | CatBoost | LightGBM |
| 信用需給分析 | LightGBM | 統計モデル |
| 大口投資家動向 | ルールベース | LightGBM |
| 市場環境判定 | ルールベース | HMM・Markov Switching |
| 決算・開示文書解析 | 日本語金融LLM | 日本語BERT系 |
| 戦略統合 | 固定配分 | 正則化付きメタモデル |

第一候補は最初に比較するモデルであり、最も高性能と確定したものではない。

## 7.3 特徴量

検討候補：

- 過去リターン
- 出来高変化
- 売買代金
- ボラティリティ
- 移動平均
- モメンタム
- 相対強度
- 信用残高変化
- 空売り残高変化
- 財務指標
- 業績成長率
- 業種情報
- TOPIXのトレンド
- 市場全体のボラティリティ

特徴量の計算は時点管理を徹底する。

財務データについては、予測時点で実際に利用可能だった値のみを使用する。

## 7.4 予測対象

以下を候補とする。

- 5営業日先リターン
- 10営業日先リターン
- 20営業日先リターン
- 60営業日先リターン
- TOPIXに対する超過リターン
- リスク調整後リターン

予測期間と保有期間の対応関係を検証する。

信用売りについては、買い予測の反転と独立した下落予測モデルを比較する。

## 7.5 モデル評価

必須条件：

1. 単純なモデルと比較する。
2. 訓練・検証・最終テストを分離する。
3. 未来情報の混入を禁止する。
4. 取引コスト控除後の損益を評価する。
5. 複数回のモデル探索による選択バイアスを考慮する。
6. 特定年度だけの好成績を採用根拠にしない。
7. モデルを複雑化する際は改善の再現性を確認する。
8. 予測精度と投資収益を区別して評価する。

## 7.6 LLMの用途

GPT系モデルや金融向けLLMは、主に以下に使用する。

- 決算短信の構造化
- 開示文書の分類
- 業績修正理由の抽出
- リスク情報の抽出
- 情報源の整理
- 分析結果の説明

LLMの推測だけを根拠として発注してはならない。

数値は原資料と照合し、出典を追跡できる形式で保存する。

## 7.7 第3段階の完了条件

- 各モデルが再学習可能
- 特徴量と予測値を再現可能
- 学習・検証履歴を保存
- ベースラインと公平に比較
- 未使用期間で評価
- 過剰最適化について監査
- 不採用モデルの結果も保存

有意な改善が確認できない場合は、単純なモデルを採用する。

# 第9章　第4段階：楽天証券RSS自動発注

## 9.1 開発目標

バックテストと模擬運用で検証した売買戦略を、楽天証券の注文機能に安全に接続する。

使用するインターフェースは、マーケットスピード II RSSを基本とする。

## 9.2 必須機能

- 注文前リスクチェック
- 現物買い
- 現物売り
- 信用新規売り
- 信用返済買い
- 注文状態確認
- 約定照合
- 注文取消
- 建玉照合
- 注文ログ保存

## 9.3 安全装置

3. 最大注文金額制限
4. 最大建玉制限

9. 通信障害時の安全停止

11. 再起動時の状態復元
12. ログの完全保存

注文送信後に通信エラーが発生した場合、未発注と決めつけて再送信してはならない。

証券会社側の注文状態を確認してから処理する。

## 9.4 実取引の制限

実取引機能は初期状態で無効とする。

- モック環境
- 発注しない模擬売買
- 実データでのペーパートレード
- 限定的な実運用

の順に進める。

実資金を使用する注文は、ユーザーの明示的な承認があるまで実行しない。

## 9.5 最終監査

GPT-6 Astra / Highを推奨する。

以下を重点的に監査する。

- 注文状態遷移
- 二重発注
- 誤発注
- 通信断
- 注文取消失敗
- 建玉不一致
- 信用売り規制
- 想定外の注文数量
- PC再起動
- Excel・RSSの異常停止

自動テストだけでなく、模擬障害試験も行う。
