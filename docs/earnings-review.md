# 決算をまたぐ候補の寄り前確認と見送り効果

2026年11月16日からの前向き研究。仮説は「買付寄付から予定決済寄付までの間に決算発表予定のある銘柄を見送ると、費用控除後損益と最大下落率が改善する」。現行・3条件追加の双方について、既存4口座と独立した参考計算で試す。過去期間を使って閾値を調整しない。

## 予約と証拠

平日20:10の evening で [JPXの決算発表予定日](https://www.jpx.co.jp/listing/event-schedules/financial-announcement/index.html) の当日掲載Excelを取得する。日足や日証金の翌営業日用入力と同じ選定日23:59:59 JSTが締切。ページ、各ファイルのURL・原本・SHA-256、行から抽出した予定日、実際の観測・利用可能時刻を data/swing-forward/earnings/ に版別に保存する。公式発表時刻は不明として扱う。単独の取得は swing_forward earnings。寄り前処理は選定日に保存した締切前の最新版を検証し、preopen.json にその版を固定する。

JPX無料表は特定決算期・対象会社からの報告に基づく。予定変更や未掲載企業がある。買付日より後、決済日より前の日付が確認できる銘柄だけを during_hold にする。買付日・決済日と同日は boundary_time_unknown、掲載があるが範囲外は outside_hold、予定日が未定は date_unknown、異なる日付の競合は conflicting、読み取った全表に該当銘柄なしは not_listed、締切前の証拠がない・原本検証失敗は unavailable。後から判明した実際の発表日で寄り前の判定を置き換えない。

サブエージェントには review-input.json の earnings_source を渡す。独立に選んだ候補のコードを、manifest.json と同じ場所の events.json（5桁コード → [予定日, 資料番号]の配列）で照合する。URLは sources[資料番号].url。実際の観測時刻は observed_at、利用可能時刻は available_at。回答 groups.current と groups.plus3 に earnings_review を足す。キーは各買い候補の5桁コード、値は state・dates（確認した全予定日の重複なし配列）・manifest_sha256。証拠不足では dates は空配列、ハッシュは null。candidate_notes に日付、出典、確認時刻、見送り仮説を記す。注記の欠落・資料と異なる主張は agent.json の earnings_issues に保存し、正しい注記として採点しない。基準口座の売買指示は独立に記録する。

## 検証方法と読み方

- 寄り前に全候補を注記する。機械2ルールそれぞれの上位5銘柄を起点に、during_hold のみを見送る参照用仮想口座を各200万円で並走させる。空いた枠は次順位で埋めない。手数料・スリッページ・100株・保有期間・権利や欠損の扱いは既存と同じ。解放された現金と残りの持ち高は参照用口座内で翌日へ引き継ぐ。既存4口座の候補・売買・採否はこの注記で変えない。
- 機械口座で実際に仮想約定した during_hold の各取引を同口座の決済に対応させる。損失なら回避できた損失、利益なら逃した利益として費用込みで集計する。決済済み0件は未評価。未約定・未決済・日程不明・同日境界は個別に計数する。全買付予定に対し、資料判定とエージェントが実際に提出した注記の両方の件数を表示する。
- close.json の earnings_counterfactual に参照用口座の取引と残高、reviews/YYYY-MM-DD.json の earnings_review に上記の集計と、比較元・参照用口座の最大下落率および損益差を保存する。個々の取引を除いた損益と、解放された資金で以後の取引が変わる口座全体の成績は別の指標。
- 原因は当日の記録で確認する。候補条件は preopen.signal.universe_exclusions と候補別 plus3_exclusions、判断の差は agent.differences、資金不足・既保有・欠損は skips・coverage・fills、各日までの件数は earnings_review を使う。これだけで決算が値動きの原因だったとは断定しない。
- 初回のレビューでは確定数と未評価数を併記する。見送りで費用後損益も最大下落率も改善しない場合は仮説を支持しない。片方だけの改善、確認不能の多さ、少数例では継続検証とする。反証可能な次の仮説は一度に一つとし、根拠・検証開始日・見送り条件をGitHubに先に残す。引け後の担当は反復した差を原本で確認できたときに trade_decision に分析を依頼する。日別の findings.json に根拠、反証条件、次の仮説（根拠不足は null）を保存する。自動採用や実注文への接続は行わない。
