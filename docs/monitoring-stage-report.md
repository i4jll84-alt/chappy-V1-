# 保存済みモック状態の監視

## 対象と位置づけ

Excel未導入のため、ユーザー指示によりRSS実接続を保留した。
第5段階の初期部分として、既存モック注文管理の状態を読み取る。
実市場の運用監視や第5段階全体の完了を意味しない。

```powershell
.\.venv\Scripts\python.exe -m trading_system.cli monitor-mock --output data/monitoring/current.json
```

既定では `data/execution-mock/manager.sqlite` を読む。
別のモックDBは `--database` で指定する。存在しないDBを作成しない。
APIキー、Excel、ネットワーク接続は不要。

## 監視内容

- 保存された注文状態と件数、数量、現金・保有数量。
- 緊急停止・照合不確実性、送信中や取消中などの状態。
- 未完了注文の期限、保存済み根拠の鮮度。
- モック設定の固定価格で計算した評価額。
- 過去の口座照合記録。今回の独立した口座照合ではない。

初期残高と保存済み約定の数量・価格・手数料から、現在残高との集計整合を検査する。
不一致、根拠が未来または期限切れの場合は評価額を未算出とする。
これは同じDB内の整合検査であり、証券会社側の残高を確認するものではない。

実現損益・含み損益・最大ドローダウンは、この監視だけでは確定できないため未計算とする。
モデル劣化、実API・RSSの稼働状態、実口座の余力・信用維持率も監視対象に含まない。
既存の資金拘束・余力検査を補助的に使用するが、新規注文時にだけ適用する
全リスク上限の再検査ではない。監視結果から発注可否を判断しない。

SQLiteを読取専用で開き、トランザクション内の一貫した状態を読む。
注文管理クラスを初期化しないため、起動時の注文回復、送信、取消、停止解除を行わない。
注文DBの上書きを防ぐため、レポート出力はJSON形式で、状態DBのディレクトリ外に限定する。

## 時刻と判定の意味

通常は実行時のUTCを使う。`--observed-at` でタイムゾーン付き時刻を明示できるが、
これは合成シナリオの検査時計であり、その時刻の過去DBを再現する機能ではない。
常に現在保存されている状態を読む。

```powershell
.\.venv\Scripts\python.exe -m trading_system.cli monitor-mock --observed-at 2026-01-05T01:00:00+00:00 --output data/monitoring/demo.json
```

既存モックデモは1月5日の固定根拠を使用し、最後に緊急停止を設定するため、
現在時刻で読むと古い根拠と停止を検出するのが正常である。
`observed`（終了コード0）は検査した範囲で注意項目がないことに限る。
`attention`（終了コード3）は注意項目があることを意味する。
読取不能・入力不正は終了コード2。いずれも実運用や取引の許可を表さない。

監視は要求されたときに1回実行する。常駐処理、自動通知、自動復旧は含めない。

## 保存済みDBでの実行確認

既存の注文3件（約定済み2件・取消済み1件）、モック現金89,995.20円、
MOCK-A保有100株、緊急停止あり・照合不確実性停止なしを読み取った。
初期残高と3約定の集計は保存残高と一致した。

現在時刻では根拠期限切れ・ルール期限切れ・緊急停止・資金検査不可を報告し、
評価額はnull。デモの固定時刻では緊急停止のみを報告し、合成固定価格による
評価額99,995.20円を算出した。すべて注意ありの終了コード3だった。

固定時刻での2回の結果JSONはバイト単位で一致した。3回の実行前後で、
注文側・モック側の両DBのSHA-256が変わっていないことも確認した。
結果はGit対象外の `data/monitoring/current.json`、`demo.json`、`demo-repeat.json` に保存。
SQLiteは読取時にも共有メモリ等の補助ファイルを扱う場合があり、全ファイルシステムへの
書込みが一切ないという検証ではない。注文・残高・停止状態を変更しないことを検査した。
