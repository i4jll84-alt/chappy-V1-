# TOPIX・財務概要データ設計

この文書は第1段階で追加したJ-Quants V2のTOPIX日次と財務・決算概要を記録する。対象API、プラン範囲は[公式仕様一覧](official-specs.md)、共通の保存・再開・品質管理方針は[第1段階設計](architecture.md)を参照。

## APIと取得範囲

TOPIXは `GET /v2/indices/bars/daily/topix` を使用し、`from` と `to` で期間を指定する。返却項目は日付と始値・高値・安値・終値（Date、O、H、L、C）。休場日は行がなく、null行が返る仕様ではない。休場日の欠落を品質異常としない。

財務概要は `GET /v2/fins/summary` を使用する。`code`、`date` のいずれか、または両方が必要である。日付は開示日の検索条件であり、期間指定を仮定しない。Standardで利用できるのは財務概要で、詳細財務はPremium対象の `/fins/details` である。提供範囲・収録開始日は契約プランと公式データ仕様表に従う。

両APIともページングを最後までたどる。各ページのRaw本文を先にファイルとして永続化し、その後、ページ行・正規化行・次ページcheckpointを同一DuckDBトランザクションで確定する。ファイルシステムとDBを跨ぐ原子的確定ではないため、クラッシュ時にDB未登録のRawファイルが残ることがある。DBを確定状態の基準とし、孤立Rawを自動削除しない。API応答間で提供元データが更新される可能性があり、複数ページが同一スナップショットである保証はない。保存先は `data/jquants/market_financial/<dataset>/`（`topix`、`financials`）で、各datasetに独立したcatalogを置く。

## 版と欠損の扱い

TOPIXの自然キーは `TOPIX + Date`。始値・高値・安値・終値を検査し、正の有限値とOHLC整合性を要求する。nullを含む行は品質異常としてRawを保持する。APIが返さない休場日を合成しない。

財務概要の自然キーは `Code + DiscNo`。`DiscDate` と `DiscTime` は別の開示項目であり、決算対象期間では自然キーを作らない。`--date` は開示日の完全一致で絞り、`--code` のみなら契約プランで取得できる利用可能な履歴を対象とする。開示番号が異なるレコードを自動で訂正前後と結び付けない。公式仕様に訂正フラグがなく、開示番号も時系列順とは限らないためである。

同一自然キーと同一内容・同一品質判定の再取得では新しい内容版を作らず、観測履歴を追加する。内容または品質判定が変わった場合は前版を残し、新版を作成する。提供元が同じキーの値を上書きした場合も、この方法で観測した変更を保持する。公式数値項目は文字列で返るため、正規化時に十進文字列として保持し、丸めを行わない。検証対象に選んだ項目はSales、OP、OdP、NP、EPS、TA、Eq、CFO、CFI、CFF、CashEq。これらの空欄はnullとして扱い、ゼロ補完や前方補完をしない。負の利益やキャッシュフローは有効値になり得る。不正な非空数値はRawを保持して品質異常とする。その他の公式項目はRawと完全payloadに保持するが、この段階では個別の数値意味検査を行わない。

## Point-in-Time

財務の `DiscDate` と `DiscTime` はJSTの公表日時として扱う。公式仕様は秒を原データのまま収録し、値は常に `00` としているため、`HH:MM:00` を公表時刻としてUTCへ変換する。一方、実接続では `HH:MM` の応答も観測された。現実装は両表記を分精度として受け入れ、UTCの秒は `00` に正規化し、元の表記はRawに残す。保存した時刻の秒は観測された元の秒情報を意味せず、実際の公表時刻が分境界だったとの保証でもない。時刻信頼度は `publication_minute_and_observed` とする。これは公式記載と実観測の差として記録し、未知の時刻形式まで許容するものではない。時刻が空欄の場合は公表時刻を推定せずnullとし、`unknown_publication_time` の注意を記録する。不正な非空時刻は品質エラーとする。`source_updated_at` は提供元更新日時が不明のためnull。取得完了日時とは区別する。

未確定中の新規版は利用可能日時nullとする。検索条件が正常に完了した時点で、そのスナップショットに含まれる新しい版へ取得完了時刻の1秒後を設定する。財務の公表日時が確認できる場合も、取得完了前に利用可能だったとは見なさない。as-of読出しではcode/dateまたはfrom/toなどの検索条件を明示する。省略時はdataset内の最新完了検索を選ぶため、意図するスナップショットを指定する場合は条件を省略しない。最新の対象検索が `empty` または `quality_failed` の場合、過去スナップショットの値を代用しない。同じ内容・品質判定の版を再観測しただけの場合、元の観測と利用可能日時を維持する。`topix_current` と `financial_current` は監査用の最新ビューであり、as-of結果を示さない。

過去日付の開示データ自体を取得できる場合がある一方、取得開始前に観測されていない提供元の旧版、後から上書きされた旧値、当時の取得・提供状況は復元できない。したがって初期取得以前の時点を完全に再現できるとは主張しない。

## 品質・運用上の制約

品質異常の行やRawは自動削除・補完しない。取得ジョブの完了状態は応答と保存処理の完了を示すもので、取引日カレンダーとの照合や未収録日の網羅性を意味しない。

DuckDB catalogを確定状態の基準とする。Parquet出力時はファイル群の世代切替とDuckDBの完了状態確定を跨ぐ単一トランザクションがないため、強制終了時に `latest.json` がDBより先の世代を指す可能性がある。異常終了後はParquet一覧だけを信頼せず、同じ条件でコマンドを再実行してDBから再出力し、確定状態を確認してから利用する。Parquet世代と `latest.json` は監査用のエクスポートで、単独ではPoint-in-Time安全性を持たない。Point-in-Time読出しには確定済み検索条件を用いる。

完了確定はfetched、または最終ページ取得後のexport_failed再試行に限り、保存済み最終ページの
次cursorなし・ページ番号とcheckpoint一致も確認する。エラー分類だけでは完了を許可しない。
fetched・export_failed・終端ジョブへの追加ページを拒否し、終端ジョブを再finish/failして
完了時刻や状態を変更しない。DB確定後のreceipt書込み失敗でもDBの取得履歴と完了根拠を保持する。
キャッシュ再実行はHTTPなしでParquetを再生成するが、欠落したreceiptファイルの再作成はしない。

財務概要には多数の項目があり、空欄の意味は項目・開示状況によって異なる。空欄をゼロと解釈しない。修正開示の判定を開示番号だけから推測しない。調整値やTOPIXの過去訂正履歴がAPIで全件提供される保証もない。

財務API専用レート枠は毎分60回で、通常API枠とは独立している。契約プランによるデータ範囲制限は別途適用される。
