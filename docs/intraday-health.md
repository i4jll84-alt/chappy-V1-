# ザラバ中の自動稼働確認

## 実行条件

Windowsタスクで個別株ツール本体、楽天分足、カブコム板を確認する。
Codexプロセス・Codex API・AIモデルを呼び出さず、ローカルのプロジェクトPythonだけで動く。
PCの起動とWindowsへのログインが必要。電源オフやログアウト中の実行はできない。
スリープ解除を強制する設定にはしていない。

- 平日の取引日に9:30と10:30を必ず確認する。9:30が正常でも10:30は省略しない。
- 異常が残る場合は30分枠ごとに再確認する。回復したら追加確認を終了する。
- 昼休み11:30〜12:30は新たな点検を延期し、12:30に再開する。
- 休場日と15:30以降は取得の点検・復旧を行わない。取引日は保存済み公式カレンダーで確認する。
- カレンダーを確認できない場合は異常として記録し、証券アプリを操作せず次の枠で再確認する。
- PCの起動が遅れた場合は、当日の未実施回を現在時点で一度確認する。過去時刻に実行した扱いにはしない。
- 翌営業日は確認状態をリセットし、9:30と10:30から再開する。

Windowsタスク自体は9:30〜15:00の30分枠とログオン時に起動する。
9:30・10:30以外で追加確認が不要なら、状態ファイルを確認するだけで即終了する。
したがってタスク画面に次の30分枠が表示されても、正常終了後の再点検・復旧は行わない。

## 確認と復旧

OSのロック、保存済みレコードの最新時刻、実際の市場データ時刻を確認する。
通常は20秒を空けた2回の観測で、両社の保存件数が進んだことまで確認する。
保存時刻は180秒、市場データは取引時間換算300秒を鮮度の基準にする。
日付違い・未来時刻を正常とせず、昼休みの経過は市場データの古さに含めない。
ライブDBは主キー末尾の限定件数を読み、全表集計をしない。

未約定銘柄の分足なしや直近の一時的なExcel読取拒否だけで、取得全体の停止とは扱わない。
これは稼働・更新の監視であり、全銘柄・全時刻の完全性を保証する日次品質検査ではない。

自動復旧は、停止したツール・取得処理の起動、必要な証券アプリや生成済み研究用Excelの起動、
更新が停止した取得ループへの協調停止・再起動要求を行う。
片社のログイン待ちや復旧失敗が、もう片社の起動を妨げない。
復旧を要求した場合は75秒後に再検証し、起動要求だけで復旧成功とは記録しない。

実行中の取得には専用のhealth-restart.jsonを渡す。対象は要求より前に起動した処理のみ、
有効期間は2分。取得途中のレコードを保存し、通常の終了処理を通してから再起動する。
終了確認は最長60秒で、応答しなければ強制終了せず未解消として次の枠へ回す。
15:25以降は引け直前の稼働中処理への再起動要求を控える。
既存のSTOP・STOP.resumingは解除しない。認証情報は保存しない。

kabuステーションのログインやAPIパスワード再入力、楽天のログイン・RSS接続操作が
必要な状態は人の操作待ちになる。未知のプログラム不具合を無人で書き換える機能ではなく、
既知の復旧操作を行い、未解消の原因と必要な操作を記録する。
取引ルール変更、実注文、データの捏造・欠測補完は行わない。

## 構成と操作

- intraday_health：日程判定、軽量読取、復旧要求、再検証、結果保存。
- intraday_health_worker：ツール本体・楽天・カブコムの独立したWindows復旧タスク。
- capture_control：手動停止と分離した、期限付きの協調再起動要求。

プロジェクトのPowerShellから以下を実行する。

~~~powershell
.\scripts\register_intraday_health.ps1 -Preview
.\scripts\register_intraday_health.ps1
.\.venv\Scripts\python.exe -B -X utf8 -m trading_system.intraday_health --inspect
~~~

登録タスクはJPX-IntradayHealthと、末尾Desktop / Rakuten / Kabucomの復旧用3タスク。
復旧用タスクには定時トリガーを付けず、異常がある場合だけ確認タスクが呼び出す。
対話ユーザー・一般権限で実行し、多重起動はIgnoreNewと既存のOSロックで防ぐ。
復旧ワーカーは短い点検タスクと別のタスクなので、点検終了時に巻き込んで終了しない。

監視を停止するにはJPX-IntradayHealthを無効化するか、
data/intraday-health/STOPを作成する。既に稼働中のデータ取得を止める操作とは分離している。

結果はdata/intraday-health/status.json、state.json、
runs/YYYY-MM-DD/、workers/にローカル保存する。
ワーカーの例外は種別・SQLiteエラー名・コード位置のみを残し、例外メッセージや認証情報は記録しない。
取得原本や結果、タスクXMLはGitHubへ送信しない。

## 検証と適用時期

日程の境界、正常時終了、30分再確認、休場・昼休み、日付変更、
片社の認証待ち、手動停止、更新停止、協調停止での原本保存を隔離テストする。
実機ではWindowsタスクの実行、両社の更新、正常後の再呼出しで追加点検しないことを確認する。
既に動いている収集プロセスへの協調停止の追加は、そのプロセスの次回起動から有効になる。
正常な取得を止めて再読込する検証は行わない。
Codex自体を終了させる試験は行っていない。実行ファイル・依存関係・タスク実行が
Codexプロセスを要求しないことを確認する。将来の定刻実行そのものは未観測。
